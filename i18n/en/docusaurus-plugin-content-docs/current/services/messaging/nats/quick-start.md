# Get started with NATS

:::info Availability
NATS is not yet available as self-service in the [Hikube console](https://console.hikube.cloud).
To provision an instance or change its configuration, [contact support](mailto:support@hidora.io).
:::

This guide explains how to get a **NATS cluster** on Hikube and run your first publish and consume tests with the `nats` CLI.

---

## Objectives

By the end of this guide, you will have:

- A **NATS cluster** provisioned in your Hikube project, with **JetStream** enabled
- A **user** to connect to the cluster
- Created a stream, and published and consumed a first message

---

## Prerequisites

- A **Hikube account** and a **project** (see the [Hikube quick start](../../../getting-started/quick-start.md))
- The **NATS CLI** (`nats`) installed on your workstation, available from [nats-io/natscli](https://github.com/nats-io/natscli)

---

## Step 1: Prepare your request

Gather the parameters of the instance you want:

| Parameter | Description | Example |
|-----------|-------------|---------|
| Project | Hikube project in which to create the instance | `demo01` |
| Name | Name of the NATS instance | `events` |
| Replicas | Number of NATS servers (3 for JetStream high availability) | `3` |
| Preset | CPU/memory profile (see [Concepts](./concepts.md#resource-presets)) | `small` |
| JetStream | Enablement and size of the persistence volume | Enabled, `10 GB` |
| Users | Names of the accounts to create | `user1` |
| Advanced configuration | NATS parameters to adjust (`max_payload`, `write_deadline`…) | `max_payload: 16MB` |
| External access | Whether or not to expose the cluster outside the platform | No |

---

## Step 2: Request the instance

Send these parameters to support at [support@hidora.io](mailto:support@hidora.io), or via the **Contact support** button in the console's profile menu.

Support sends you back:

- the NATS **server URL** (written `<nats-url>` in the rest of this guide);
- the **credentials** of the requested users.

:::note
The standard NATS client port is `4222`. With external access, TLS is enabled automatically: connect with `tls://` and trust the certificate authority that support sends you. User passwords are generated by the platform. Always use the address and port provided by support.
:::

To avoid repeating the URL and credentials, save a context in the CLI:

```bash
nats context save hikube --server <nats-url> --user <user> --password <password> --select
```

---

## Step 3: Create a JetStream stream

```bash
nats stream add EVENTS \
  --subjects "events.*" --storage file --replicas 3 --retention limits \
  --max-msgs -1 --max-bytes -1 --max-age 24h --discard old --defaults
```

:::note
The number of replicas of a stream cannot exceed the number of NATS servers in the instance.
:::

---

## Step 4: Publish and consume a message

```bash
# Publish a message
nats pub events.test "Hello Hikube!"

# Read the contents of the stream
nats stream view EVENTS
```

**Expected result:**

```console
[1] Subject: events.test Received: 2025-01-15T10:30:00Z
  Hello Hikube!
```

---

## Step 5: Quick troubleshooting

### Connection refused

```bash
nats server check connection
```

**Common causes:** wrong URL or port, wrong credentials (`Authorization Violation`), external access not enabled while you are connecting from outside the platform.

### JetStream not working

```bash
nats account info
```

**Common causes:** JetStream not enabled on the instance, insufficient JetStream storage space, number of stream replicas greater than the number of servers.

### Cluster-side issue

If the cluster seems unavailable, [contact support](mailto:support@hidora.io), stating the project and instance names.

---

## Step 6: Cleanup

Delete the test stream from the CLI:

```bash
nats stream rm EVENTS -f
```

To delete the instance itself, send the request to [support](mailto:support@hidora.io), stating the project and the instance name.

:::warning
Deleting a NATS cluster erases all associated data, including JetStream streams. This operation is **irreversible**.
:::
