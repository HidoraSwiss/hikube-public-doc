# CLAUDE.md — Hikube Public Documentation

## Projet

Documentation publique Hikube, basée sur **Docusaurus** (v3). Hébergée sur `https://docs.hikube.cloud`.

- **Build** : `npm run build`
- **Dev** : `npm run start`
- **Servir le build** : `npm run serve`
- **Vérification** : le build ne casse pas sur les liens cassés (`onBrokenLinks: 'warn'` dans `docusaurus.config.js`) ; lire les warnings du build

## Structure du projet

```
docs/
├── getting-started/          # Introduction, concepts clés, quick-start global
├── services/
│   ├── kubernetes/           # Clusters K8s (overview, concepts, quick-start, how-to/, plugins/, faq, troubleshooting)
│   ├── compute/              # Machines virtuelles
│   ├── databases/            # PostgreSQL, MariaDB, MongoDB, Redis, ClickHouse
│   ├── messaging/            # RabbitMQ, Kafka, NATS
│   ├── storage/              # disks/ (disques), buckets/ (object storage S3)
│   ├── networking/           # VPC et sous-réseaux (menu « Réseau »)
│   └── gpu/                  # GPU as a Service
├── api/                      # API publique : overview, authentication, quick-start, errors, faq
│   └── reference/            # GÉNÉRÉ depuis l'OpenAPI (npm run gen-api-docs) : ne pas éditer
├── resources/                # FAQ, troubleshooting, glossaire
└── tools/                    # Terraform
```

### Convention par service (Diátaxis)

Chaque service suit la structure Diátaxis :

```
service/
├── overview.md          # Le quoi/pourquoi (sidebar_position: 1)
├── concepts.md          # Terminologie, architecture (sidebar_position: 2)
├── quick-start.md       # Démarrage rapide en 7 étapes (sidebar_position: 3)
├── how-to/              # Guides pratiques atomiques (autogenerated dans sidebar)
│   └── _category_.json
├── faq.md               # Questions fréquentes (sidebar_position: 6)
└── troubleshooting.md   # Dépannage (sidebar_position: 7)
```

L'ordre dans la sidebar est contrôlé par `sidebars.js` (définition explicite).
Le `sidebar_position` dans le frontmatter sert de convention de numérotation mais n'est pas utilisé par Docusaurus directement.

**Cas spécial Kubernetes** : les pages `plugins/` sont insérées entre les guides pratiques et la FAQ.

Il n'y a plus de page `api-reference.md` par service : la référence de l'API
publique est générée (voir « API publique » ci-dessous).

## Console d'abord

La doc enseigne la **console** `https://console.hikube.cloud`. Le pilotage par
kubeconfig de projet (ex-tenant) + `kubectl apply` de manifestes
`apps.cozystack.io` est **déprécié et ne doit plus apparaître**, sauf dans
`docs/tools/terraform.md` (marqué legacy, kubeconfig sur demande au support).

- Source de vérité des écrans : dépôt `frontend` (lire `origin/main`,
  libellés exacts dans `messages/fr.json`). Citer les libellés en **gras**.
- `kubectl`/`helm` restent légitimes **dans un cluster Kubernetes client**
  (kubeconfig téléchargé depuis la page du cluster dans la console).
- L'API publique (clés d'API) se documente **à côté** de la console, jamais à
  sa place : voir « API publique » ci-dessous.
- Service ou option absent de la console : encadré `:::info Disponibilité`
  renvoyant au support (cas actuel : ClickHouse, Kafka, NATS).
- Terminologie : « organisation » et « projet » (plus « tenant »).

## API publique

La surface publique est celle des **clés d'API** : `public.swagger.json`
produit par `just gen_doc` dans `hikube-api`. Elle est copiée telle quelle dans
`static/openapi/hikube-public.swagger.json`. **Ne jamais publier
`frontend.swagger.json`** ni documenter une opération absente de la surface
publique (IAM, compte, organisation, projet, gestion des clés, événements).

- **Référence générée** : `docusaurus-plugin-openapi-docs` génère
  `docs/api/reference/` (pages et `sidebar.ts`). Après mise à jour de la spec :
  `npm run clean-api-docs && npm run gen-api-docs`, puis commiter le résultat.
  Ne pas éditer ces fichiers à la main.
- **URL centralisée** : l'URL de base n'est définie qu'à un endroit,
  `HIKUBE_API_URL` dans `docusaurus.config.js` (exposée en
  `customFields.hikubeApiUrl`). Dans les pages : `<HikubeApiUrl />` et
  `<ApiEnv />` (`@site/src/components/HikubeApi`) ; dans les exemples `curl`,
  `$HIKUBE_API`. Ne jamais écrire l'URL en dur.
- **Exemples `curl`** : variables `$HIKUBE_API`, `$HIKUBE_API_KEY`,
  `$PROJECT_ID` (définies dans `docs/api/quick-start.md#environnement`),
  en-tête `X-Hikube-Api-Key`. Chemins, champs (camelCase) et contraintes
  exacts d'après la spec ; vérifier dans `hikube-api` si un `PATCH` remplace
  toute la configuration. Clé fictive uniquement : `sk_hk_<keyId>_<secret>`.
- **Onglets « Console | API »** dans les quick-starts et how-to des services
  exposés : `Tabs`/`TabItem` de `@theme/Tabs`, `groupId="interface"`, onglet
  `console` en premier avec `default`. Le texte console reste inchangé dans
  son onglet. Si l'opération n'est pas dans la surface publique, l'onglet API
  le dit et renvoie à la console.
- **Préversion** : l'API est en `v1alpha1` ; le dire dans un encadré
  `:::warning Préversion` sur les pages de `docs/api/`.
- **Clés d'API** : pas encore d'écran dans la console ; la création passe par
  le support. Mettre à jour `docs/api/authentication.md` quand l'écran arrive.

## Conventions de rédaction

### Langue
- Contenu principal en **français** (locale par défaut)
- Traductions dans `i18n/<locale>/` (`en`, `it`, `de`)

### Manifestes YAML
- Plus de manifestes de ressources Hikube (`apps.cozystack.io`) hors Terraform legacy
- **Ne jamais inclure `namespace: default`** dans les exemples YAML
- Toujours ajouter `title="fichier.yaml"` sur les blocs code YAML

### Structure des quick-starts
Suivre le modèle en **7 étapes** (cf. `docs/services/kubernetes/quick-start.md`) :
1. Créer le service (menu de la console, bouton de création)
2. Configurer et valider (champs de l'assistant, récapitulatif)
3. Vérifier l'état (statut dans la console, résultat attendu)
4. Récupérer les identifiants (où ils sont dans la console)
5. Connexion et tests (client natif)
6. Dépannage rapide
7. Nettoyage (suppression depuis la console)

### Admonitions Docusaurus
Utiliser `:::tip`, `:::note`, `:::warning` pour les encadrés importants.

### Diagrammes
Mermaid est supporté nativement (blocs ` ```mermaid `).

## Pièges connus

- **RabbitMQ, NATS, Kafka** sont sous `services/messaging/`, pas `services/databases/`
- La console dit **MariaDB** (pas MySQL) : le dossier est `services/databases/mariadb/`
- Les presets de ressources (`resourcesPreset`) sont partagés entre tous les services DB : nano, micro, small, medium, large, xlarge, 2xlarge
- Si `resources` (CPU/mémoire explicites) est défini, `resourcesPreset` est ignoré
- Les opérateurs varient par service : Spotahome (Redis), CloudNativePG (PostgreSQL), etc.
- `onBrokenLinks: 'warn'` : le build ne casse pas sur les liens cassés, il faut vérifier les warnings manuellement
